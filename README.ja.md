# Pull-Based AI Intelligence Digest（日本語版）

**言語: [English](./README.md) · 日本語**

> 1つの Claude Project の中だけで完結する、ステートフルな「AIニュース＋スタートアップ投資アナリスト」。バックエンドも、データベースも、常駐ジョブもない。記憶はバージョン管理された1つの状態ファイルに宿り、規律ある「State Loop（状態ループ）」が、あるセッションの学習を次のセッションへ運ぶ。

> **Note.** これは英語版 `README.md` の逐語訳ではなく、設計思想と実運用の判断を厚めに述べた日本語版です。プロダクトの正本ドキュメントは英語版で、本書はその設計思考を日本語で読むための派生版です。

---

## Overview（概要）

多くの人は大規模言語モデル（LLM）を *ステートレス*（状態を持たない）な道具として使う——チャットを開き、プロンプトを貼り、答えを得る。そしてタブを閉じた瞬間、モデルがあなたの好みについて「学んだ」ことは蒸発する。このプロジェクトは、同じモデルを *ステートフルで Pull 型のアナリスト* として扱う。

ここでの **Pull 型** とは「裏で常駐して勝手に動く仕組み（Push 型）を持たず、人間がセッションを起こしたときにだけ、モデルが状態を読み込んで推論する」設計を指す。毎セッションは、1つの正本状態ファイル——どのスタートアップを既に分析したか、読み手の好みがどう変化したか、前回どう判断したか、というシステムの記憶——を読むことから始まり、そのファイルを**丸ごと書き換えて**終わる。だから次のセッションは、その変化を引き継ぐ。

運用上のアウトプットは2つ。**Daily Digest（日次ダイジェスト）**——その日の重要AIニュース Top 5 を、固定された6軸ルーブリック（採点基準表）で 0–100 点に採点する。うち1枠は必ず「🔬 Breakthrough Spotlight（技術ブレイクスルー枠）」に割り当て、真に新規な成果が加重平均に埋もれないようにする。そして **Startup Investment Report（スタートアップ投資レポート）**——構造化された分析（投資仮説・堀・リスク・スコア・判定）を、重複防止レジストリ（登録簿）に紐づける。だから同じ企業を「新顔」として二度紹介することがない。消費はすべて日英バイリンガルの単一ダッシュボードで行う。メールもニュースレターも、第2の正本も持たない。

このリポジトリは、Claude Project で本格的なワークフローを構築したい人への **参考事例（reference example）** として公開している。面白いのはニュース要約そのものではなく、その裏のアーキテクチャだ——ステートレスなモデルにどう永続的な記憶を与えるか、そして状態を確定（コミット）する主体として、どう人間をループの中に残すか。以下の設計判断と、注釈付きのバージョン履歴こそが本題である。

## Key Design Decisions（設計判断）

このシステムを形づくった判断は4つ。後半2つには一貫した思想が通っている——**スコアは「本質的な重要度」を測る純粋で比較可能な指標に保ち、鮮度も外れ値の救済も、スコアを汚さずに一段上の“選定層”で解く。** メトリクス（測る物差し）と運用ロジック（どう選ぶか）を分離しておくと、両方が正直に保てる、というのが実運用で得た教訓だ。

### 1. Push 型ではなく Pull 型を選んだ
- **決定**：毎セッションが状態ファイルを読み、推論し、丸ごと書き直す。差し替えの確定は人間が行う。
- **却下した代案**：定時にニュースを取得して通知する Push 型パイプライン。
- **なぜ却下したか**：Push 型は「誰かが保守し続けねばならないインフラ」であり、他人がフォークして5分で動かすことができず、記憶（状態）を裏側に隠してしまう。Pull 型なら状態が全て人間可読・監査可能で、Claude Project さえあれば誰でも移植でき、「何を記憶するか」を決める人間がループに残る。
- **支払う代償**：リアルタイム通知はない。私がループを回さない限り、何も起きない。この「能動性の欠如」は、移植性と監査可能性を得るために意図的に受け入れたトレードオフだ。

### 2. Business Impact（事業インパクト）を最大の重み（25）にした
- **決定**：私は *経済がどう書き換わるか*——価格、ユニットエコノミクス（単位あたり経済性）、原価構造——を最も重視する。それが私の見たいレンズだからだ。
- **相対的な判断**：企業の *内在的な優位性*＝技術とビジネスモデルを、市場規模より上位に置いた。市場規模（Market）は 15 に下げている。市場規模は、事業そのものの駆動力というより、投資家が物語に被せるフレーミングに近いと考えるためだ。
- **トレードオフ**：事業インパクト優先の重み付けは、商業的含意がまだ表に出ていない純粋な研究成果を過小評価しうる。この穴は、下の Spotlight ルールで塞いでいる。

> 補足：ここで加重平均（各軸の点数を重み付けして足し合わせる方式）を採る以上、単一の軸で突出した成果は平均に薄められる。だからこそ判断4の Spotlight が対になっている。

### 3. 鮮度（Recency）はスコアではなく“選定”で扱う
- **決定**：ニュースは新しくあるべきだが、スコアの式に鮮度の項は入れない。鮮度は一段上の「候補取得」段で担保する——日次の候補プールを直近3日以内に限定し（静かな日だけ7日へ自動拡張）、各アイテムに発表日を必ず明示する。
- **却下した代案**：スコアに recency-decay（時間経過で減点する項）を入れること。
- **なぜ却下したか**：それは日をまたいだ比較可能性を壊す。ブレイクスルーは2日経ったからといって *重要度が下がる* わけではない。「72点」はいつ読んでも同じ意味であるべきだ。鮮度を取得層に置けば、スコアは本質的重要度の安定した尺度でいられる。
- **意図的な例外**：Spotlight 枠だけは窓を緩める。真に新規な技術成果は、発表から数日遅れて理解・波及することが多いからだ。

### 4. 素の加重平均に、Spotlight 枠で救済をかける
- **決定**：スコアは純粋な加重平均——ボーナス項は一切ない。
- **既知の弱点**：平均は、単一の軸で振り切れた成果を薄めてしまう。だから本物のブレイクスルーが平凡な点数になり、埋もれうる。
- **却下した代案**：ブレイクスルーを持ち上げるために式へ max 項やボーナス項を足すこと。
- **なぜ却下したか**：それは「その数字が何を意味するか」を濁らせる。一度スコアが“平均＋ボーナス”の混合物になると、アイテム間の比較が破綻する。
- **代わりに選んだ解**：問題を選定層で解いた。5枠のうち1枠を、その日の max(Technology, Novelty) が最大のアイテムに必ず割り当てる。スコアは水増しせず正直なまま。メトリクスは純粋に保たれ、それでもブレイクスルーは必ず浮上する。**判断3と同じ原則——問題は、それが属す場所で解く。スコアを汚さない。**

## Design Philosophy（分析の姿勢）

このシステムの役割は「ニュース要約者」ではなく *アナリスト* である。すべてのアイテムは6つのレンズを通される——何が起きたか／なぜ重要か／誰が得をするか／誰が脅かされるか／次に何が起きるか／投資・事業上の含意。「何が起きたか」で止まる要約は、失敗とみなす。

その下に2つの原則（Doctrine）が敷かれている：

- **一次情報を最優先する。** 企業の公式開示、論文、SEC（米証券取引委員会）提出書類、一次報道——アグリゲータや二次まとめは補助であって、根拠の土台にはしない。裏の取れない主張は載せない。憶測は「憶測」と明示する。
- **既定で逆張りする。** コンセンサス（大勢の見方）は、なぞる対象ではなく反論の出発点だ。どのダイジェストも、見出しが見落とした「誰が脅かされるか」や含意を、最低1つは掘り出すことを求められる。

## Features（主要機能）

- **Daily Digest** — その日の Top 5 を6軸ルーブリックで 0–100 点に採点。日英バイリンガル。
- **Breakthrough Spotlight** — 5枠のうち1枠を最も新規性の高い技術成果に必ず確保し、加重平均に埋もれさせない。
- **Startup Investment Report** — 投資ルーブリックに沿った構造化分析（仮説・堀・リスク・スコア・判定）。
- **重複防止レジストリ** — 分析前に正規化ドメインで照合し、同じ企業を「新規」として再登場させない。
- **6レンズ分析** — すべてのアイテムを要約で止めず、投資・事業上の含意まで駆動する（6レンズは Design Philosophy 参照）。
- **フィードバック駆動の Preferences** — チャットでのフィードバックが状態ファイルに蓄積し、以後の選定・採点・トーンを変える。
- **単一バイリンガル・ダッシュボード** — 消費面はこの1つのアーティファクトだけ。メールも、分岐する複製もない。

## Architecture: The State Loop（アーキテクチャ）

システムは3つの静的レイヤーと、状態を時間方向へ運ぶ1つのループから成る。

### 3層構造

```
┌─────────────────────────────────────────────────────────────┐
│  1. INSTRUCTIONS  (Claude Project → Instructions field)      │
│     Role · doctrine · hard constraints · output contracts    │
│     The rules. Rarely changes.                               │
├─────────────────────────────────────────────────────────────┤
│  2. KNOWLEDGE BASE  (Claude Project → Knowledge)             │
│     intelligence-state.md   ← the only source of truth       │
│     evaluation-framework.md ← scoring rubrics (confirmed)    │
│     category-taxonomy.md    ← the 18 categories              │
│     The memory + the measuring stick.                        │
├─────────────────────────────────────────────────────────────┤
│  3. DASHBOARD  (single artifact, EN / JA)                    │
│     Daily digest · weekly view · startup registry           │
│     The only place output is consumed. No email, no copies.  │
└─────────────────────────────────────────────────────────────┘
```

上図の3層は次の役割を持つ。**① INSTRUCTIONS（指示）** はいわば憲法——安定していて、モデルが勝手に書き換えられない場所に置く。**② KNOWLEDGE BASE（知識ベース）** は作業記憶で、`intelligence-state.md` が唯一の正本。ここで意図的に、*システムが学んだこと*（Preferences・レジストリ）を保持する `intelligence-state.md` と、*どう測るか*（重み・閾値）を定める `evaluation-framework.md` を分離している——学習内容が測定基準を汚染しないためだ。**③ DASHBOARD** は結果が生きる唯一の面。だから、突き合わせるべき第2の分岐した複製が存在しない。

### ループ

```
   ┌──────────────────────────────────────────────────┐
   │                                                  │
   ▼                                                  │
 READ state ──► REASON ──► EMIT full replacement ──► HUMAN swaps file
 (start of      (score,     (Claude writes the        (canonical
  session)      select,     entire updated state,      commit —
                de-dupe)    not a diff)                the version
                                                       increments)
```

ループを正直に保つ3つの規律：

- **まず読む。** 各セッションは `intelligence-state.md` を読むことから始まる。レジストリ（重複防止）、Preferences、前回の判断が、作業前にすべて手元に揃う。
- **差分ではなく全文を吐く。** 状態が変わったら、Claude は「42行目を直して」ではなく、コピー＆ペーストで丸ごと差し替えられる完成版を出力する。モデルは自分の記憶を確実にパッチ（部分修正）できないが、確実に書き直すことはできる。
- **確定するのは人間。** Claude は正本ファイルを書けない。人間が差し替え、バージョンが繰り上がる。この1手の手動ステップこそが、記憶を信頼できるものにし、履歴を監査可能にする。

> このリポジトリは **手動ループ** を canonical（正典）として記載している。環境に依存せず、誰でもフォークできる移植性の高い版だからだ。私自身の稼働インスタンスは後にファイル差し替えを自動化したが、それはこのモデルの上に乗せた最適化であって、モデルそのものの変更ではない。

## Operating Model & Setup（運用モデルとセットアップ）

ファイルは部品にすぎない。プロダクトの本体は、その部品の上で回す **ループ** だ。だからファイル一覧より先にこの節を読んでほしい——リポジトリを「動かない標本」ではなく「回せる仕組み」にしているのは、この運用モデルである。

### 日次／週次サイクル

このシステムは *Pull 型* だ。自分では何もしない。あなたが回す。

**日次（1日1会話）：**
1. Project で新しいチャットを開く。Claude はまず `intelligence-state.md` を読む（レジストリ・Preferences・前回の判断）。
2. Claude がその日の Top 5 を選定・採点する——4枠は Importance Score 順、1枠は Breakthrough Spotlight——そしてダッシュボードの `DIGEST` に日英で書き込む。
3. Claude はチャットで完了連絡：1行＋その日の「AI Signal（今日の一言）」だけ。ダイジェスト本文はチャットに再展開しない——正本はダッシュボードだけだ。
4. あなたはダッシュボードで結果を読み、チャットでフィードバックを返す（「AI Security を増やして」「この会社を追って」「これはノイズ」）。
5. フィードバックや新しい分析で何かが変わったら、Claude は `intelligence-state.md` の全文置換版を吐く。あなたが差し替え、バージョンが繰り上がる。

**週次（1週1会話）：**
- 週のニュースの再ランキングではない。Claude は *何が変化したか* を分析する——主要トレンド、台頭企業、技術シフト、投資シグナル、来週の注目——そしてダッシュボードの週次ビューを更新する。

> **なぜ「時間単位ごとに1会話」なのか。** アーティファクトは会話単位にスコープされるため、日ごと（週ごと）に新しい会話を起こすと、各ダッシュボードが清潔に保たれ、各状態差し替えが曖昧にならない。1会話に複数日を混ぜると、どの状態が最新か濁る。

### 初回セットアップ

自分のインスタンスを立ち上げる手順：

1. **Claude Project を作る。** `PROJECT-INSTRUCTIONS.md` を Project の *Instructions* 欄に貼る。
2. **知識ベースを読み込む。** `intelligence-state.md`／`evaluation-framework.md`／`category-taxonomy.md` を Project の *Knowledge* にアップロードする。
3. **ダッシュボードを配置する。** `ai-intelligence-dashboard.jsx` をアーティファクトとして開く。ダイジェスト・週次ビュー・レジストリが描画される。
4. **初日を回す。** チャットを起こして日次ダイジェストを頼む。Claude が状態を読み、Top 5 を作り、ダッシュボードを更新する。
5. **状態を確定する。** Claude が更新版 `intelligence-state.md` を吐いたら、知識ベースのファイルを差し替える。その手動の差し替えこそが State Loop だ（Architecture 参照）。

## How to Adapt / Fork（自分用への改造）

このシステムはフォークされる前提で作られている。鍵は、*自分で変えてよいレイヤー* と *設計の整合性を担うレイヤー* を見分けることだ——間違ったほうを触ると、ループは静かに壊れる。

### 安全に変えてよい — 自分のものにする

- **Preferences**（`intelligence-state.md` §2）。これは *私の* 学習済みの好み——ビジネスモデル・レンズ、ロボは原則ハード企業として見る姿勢、制御側シグナルの重視。あなたのは違うはずだ。空にして、自分のフィードバックを積ませればいい。それがシステムの正しい使い方だ。
- **Startup Registry**（`intelligence-state.md` §1）。サンプル分析（Voliro・NEURA・Apptronik）は例示。表を空にして、自分の登録を始めればいい。
- **ダッシュボードのテーマ**（`ai-intelligence-dashboard.jsx`）。色・レイアウト・言語。重要なのは `DIGEST`／`STARTUPS` のデータ契約であって、その周りのスタイリングではない。
- **ドメイン（対象領域）**。本質的には AI 専用ではない。役割とカテゴリを気候テック・バイオ・防衛に向け直せばいい。State Loop はドメイン非依存だ。

### 熟慮の上で変える — ここに設計が符号化されている

- **スコア重みと Verdict 閾値**（`evaluation-framework.md`）。Business Impact 25、投資評価の技術優先レンズ、Verdict のバンド——これらは既定値ではなく *判断* だ。自分の投資仮説に合わせて再調整してよいが、それは熟慮した選択として行い、記録すること（フレームワークをバージョン管理しているのは、まさにこのためだ）。
- **18カテゴリ**（`category-taxonomy.md`）。集合として整合が取れている。場当たりでなく、意図して追加・統合すること。

### 壊してはいけない — 荷重を支える不変条件

- **まず状態を読む／全文を吐く／人間が確定する。** この3つのループ規律（Architecture 参照）が、記憶を信頼できるものにしている。差し替えは自動化してよいが、規律は保つこと。
- **単一の正本。** ダッシュボードの `DIGEST` が正本。他は全てその機械的レンダーにすぎない。第2の複製を分岐させないこと。
- **記憶と測定の分離。** `intelligence-state.md`（学んだこと）と `evaluation-framework.md`（測り方）を分けたまま保つ。統合すると、分離が防いでいたバイアスが再び混入する。

> 目安：**知識ベースのデータ**（Preferences・レジストリ・テーマ）はあなたが埋めるもの。**ルーブリック**は、一度、意図して再決定するもの。**ループの不変条件**は、そのまま受け継ぐ部分だ。

| **0.2** | ダイジェストが一般的すぎ、私の実際のレンズ（ビジネスモデル、ユニットエコノミクス）が反映されていなかった。 | Preferred Analysis と Presentation Preferences を追加——フィードバックループへの最初の実入力。 |
| **0.5** | あるロボティクス企業（NEURA）をハードとして採点していたが、Business と Competition の見立てが甘かった——設置台数の裏づけがないまま、プラットフォーム／ネットワーク効果の上振れを織り込んでいた。 | 同じレンズを単位あたり経済性（粗利・BOM＝部品表原価・歩留まり）へ厳格化し、未実証のプラットフォーム物語を割り引いた：73 → 67。「設置台数が証明するまでプラットフォーム物語は割り引く」を常設 Preference として明文化。 |
| **0.10** | ニュースの静かな日に、直近3日窓では候補が足りず、弱いネタで枠を埋めたくなる誘惑があった。 | **選定 Preference 層**を新設：取得を直近3日窓に限定し、良質候補が5本未満の日だけ7日へ自動拡張——スコアの式とは別レイヤーで。 |
| **0.12** | ダイジェストが能力（capability）偏重で、「能力 vs 制御」の *制御* 側（安全・ガバナンス・組織/人事の後退）が落ちていた。 | 候補選定に**制御レンズ**を追加——ガバナンス系のシグナルが、純テック案件より点が低くても Top 5 の枠を取れるようにした。 |
| **0.15** | ループが実証された後は、毎セッション手動で状態を差し替えるのが摩擦になった。 | 自分のインスタンスに限り直接ファイル書き込みを承認——これは *運用上* の変更のみ。公開する canonical ループは手動（移植性重視）のまま。自動化はその上に乗せた層。 |

この履歴が示したいことは2つある。**第一に、修正は1つの本能に集約する**——スコアの問題が現れたとき、私はスコアを汚さず、選定層で直した（0.10、0.12）。Key Design Decisions で述べたのと同じ原則だ。**第二に、私は根拠が甘いとき、自分の分析を自分で下方修正する意思を持っていた**（0.5）。それこそ、この State Loop 全体が強制しようとしている規律である。
